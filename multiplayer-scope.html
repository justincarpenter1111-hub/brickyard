Brick Builder · Engineering Scope

Online multiplayer

Two people building in the same world from different machines. This is what it takes, what it costs, and the four decisions I need from you before writing any of it.

Target: block-build.netlify.app Est. 9–14 dev days Status: not started
01The short version

The hard part is already done, and not by accident. Every change to the world funnels through createBrick / destroyBrick / moveBrickTo and then pushOp → commit(). That single choke point is where network sync taps in. Per-brick ownership already exists and is enforced on all five destructive paths.

What's missing is a server. Netlify is static hosting — it cannot hold a WebSocket open. So multiplayer means adding one small always-on service alongside it. That is the only structural change to how this project ships.

Recommendation: one room = one Cloudflare Durable Object, via PartyKit. The room owns the authoritative world, validates every op, and broadcasts accepted ops. Netlify keeps serving the game itself.

02Measured, not guessed

I measured the real payloads in the running app before choosing an architecture, because the answer changes completely depending on how big a world is on the wire.

Payload sizes — measured in browser, gzip via CompressionStream

34 KBVillage II full snapshot, gzipped (8,581 bricks)
196 KBGrand Village full snapshot, gzipped (50,000 bricks)
107 BOne place/delete op on the wire
59 BOne presence tick (position, yaw, camera)

Two conclusions. First, even the worst-case world is a 196 KB one-time cost on join — entirely survivable, so we don't need CRDTs or chunked streaming. Second, ops and presence are so small that bandwidth is a non-issue; the cost driver is message count, not size.

The join shortcut

Both villages are generated from a fixed seed — rng(31415926) for Village II. So a joining client doesn't need the brick list at all. Send {world:"village_two", seed, ops:[…]} and let them regenerate locally. A fresh join drops from 196 KB to well under 1 KB plus whatever's been built since. Full snapshots stay as the fallback for hand-built worlds.

03Architecture

Server-authoritative, not peer-to-peer. Clients send intents; the room validates and broadcasts accepted ops with a monotonic sequence number. Clients apply ops in sequence order. A client that falls behind re-syncs from the snapshot.

Optimistic local application stays — you see your own brick land instantly, and it's reconciled (or rolled back) when the server's version of that op arrives.

Why not WebRTC peer-to-peer

Tempting, since two players need no relay. But it still needs a signalling service, and NAT traversal fails often enough that you need a TURN relay — which costs more than the Durable Object it was meant to avoid. It also makes one player the host, so the world dies when they close the tab.

Op protocol

Deliberately mirrors the existing pushOp shapes, so most of the client work is serialising something the app already produces.

// client → room
{ t:"add",   b:{id,type,color,x,z,base,rot,owner} }
{ t:"del",   id }
{ t:"move",  id, to:{x,z,base,rot} }
{ t:"door",  id, open }
{ t:"pose",  x,y,z,yaw,cam }        // presence, 5–10 Hz, not logged

// room → clients
{ seq, t:"add", b:{…}, by:2 }        // accepted + stamped
{ t:"reject", ref, why:"owned" }     // your optimistic op is rolled back
{ t:"sync", world, seed, ops:[…] }   // on join or resync
04The hard parts

These are the bits that will actually eat the time. None are blockers; all need a decision made deliberately rather than discovered in testing.

Brick IDs collide

nextId is a plain client-side counter. Two clients building at once will both mint id 8,582. Fix: namespace by player — playerId * 1e7 + n. Simpler than server-assigned ids and keeps offline building working.

Undo is the genuinely awkward one

There's one global undoStack today. With two builders that's wrong in both directions: you could undo their work, and your undo could delete a brick they've since built on top of. The rule I'd implement: you may only undo your own most recent op, and only if the target still exists and nothing rests on it. Otherwise the undo is refused with a reason. Not perfect, but predictable — which matters more.

Moving entities need one authority

The train is the awkward case: train.st and speed advance every frame on whoever is driving. The driver owns it and broadcasts pose at ~10 Hz; everyone else interpolates. Passengers ride the interpolated pose. Doors and carried bricks are just ops and need no special handling.

Trust nothing from the client

Ownership is enforced client-side now. That's a UI courtesy, not security — the room has to re-check canEdit, placement legality and grid bounds on every op. Low effort, but it must not be skipped or one stuck client can corrupt the world for everyone.

05Phases

Ordered so something playable exists after the first two days, and each phase is independently shippable. The numbering is a real sequence — later phases depend on earlier ones.

#PhaseWhat you can do at the end of itDays
1Room + presence Join a shared link and see each other's minifig walking around in real time. No shared building yet.1–2
2Shared building Place and delete bricks and see them appear for the other player. Ownership enforced server-side. ID namespacing.3–4
3Join & persist Leave and come back to the world as you left it. Seed-and-delta sync so joining is instant.2–3
4Entities & undo Trains, doors and carried bricks stay in sync. Undo behaves sanely with two builders.2–3
5Rooms & polish Named rooms, invite links, player list, reconnect handling, "player left" states.1–2

Total: 9–14 days. Phases 1–2 alone (4–6 days) deliver the thing you actually asked for; 3–5 are what make it hold up in real use.

06Running cost

Cloudflare's free tier is 100,000 requests/day, and inbound WebSocket messages bill at 20:1 — twenty messages count as one request. Outbound messages and pings are free, which suits this shape well, since one build op fans out to every player.

LoadInbound msg/sBilled req/hrAgainst free tier
2 players, presence at 10 Hz203,600~27 h/day of continuous play
2 players, presence at 5 Hz101,800~55 h/day
Building bursts~2360negligible next to presence

For family-scale use this is comfortably £0/month. Presence dominates, so if cost ever matters, drop the tick rate and interpolate harder — the change is one constant.

07Risks

Deploy  The project becomes two deploys, not one — Netlify for the game, Cloudflare for the room. Given this folder already resolves to the wrong Netlify site by default, a second target needs its deploy command written down, not remembered.

Scope  The single-file, no-build constraint holds fine on the client (the network layer is maybe 200 lines inline), but the room server is a separate small TypeScript project. That's a new thing to maintain.

Behaviour  Two people editing the same stack of bricks will produce surprises no protocol fully removes — someone deletes the brick you're standing on. Worth deciding early whether that's funny or annoying.

08What I need from you

Four decisions. Everything above assumes a default, noted in each — say nothing and I'll build to those.

  1. Who can join? Anyone with the link, or only a room you name and share? Default: anyone with the link, rooms named by URL.
  2. Two players, or more? The architecture handles 4–6 without change, but the UI (player list, colours, presence) grows. Default: build for 2, don't design out more.
  3. Does the world live on the server? Or does one player load a world and share it for that session only? Default: server-persisted, so you can come back to it.
  4. Should ownership stay strict? Right now P2 cannot touch P1's bricks at all. A shared-build mode where anyone can edit anything is a one-line change. Default: keep it strict, add a room setting later.
